# SauronID — Full Technical + Business Audit

> **Status:** historical, project-authored point-in-time review—not an
> independent audit or certification. Findings are not implicitly remediated.
> Use the current release gate, production-readiness checklist, and a signed
> external assessment for any release decision.

Date: 2026-06-25. Method: source-level read of the real programs (Rust core ~30k LOC, TS SDK, Next.js dashboard, redteam suite, migrations, CI), not the README. Seven parallel deep-read passes, cross-checked. Severities are auditor-assigned.

---

## 0. One-line verdict

A genuinely well-engineered, unusually honest **agent per-call binding leash** wrapped in a marketing layer that **oversells the parts that aren't finished** (hardware attestation, ZK soundness, multi-tenant isolation, tamper-evident audit). The core leash is real and server-enforced; most of the headline crypto/compliance claims are demo-grade, fail-open, or theater. No business model exists in the repo.

---

## 1. What the system actually is

A self-hostable Rust HTTP service (`sauron-core`) + TS client SDK (`sdk/typescript/`) + Next.js operator dashboard. It puts a cryptographic "binding + leash" in front of every action an AI agent takes:

- Each agent gets an Ed25519 proof-of-possession (PoP) key + an "A-JWT" carrying declared intent and a config checksum.
- Every outbound call must be signed over `method | path | sha256(body) | timestamp | nonce`; the server verifies the sig against the registered PoP key, enforces a ±skew window, consumes a single-use nonce, and constant-time-compares a config digest.
- Accepted actions are Merkle-committed and anchored to Solana (real) and Bitcoin/OpenTimestamps (real but defaults to mock).
- Bolt-on modules: differential-privacy cohort stats, Paillier homomorphic aggregation, Groth16 ZK proofs over the action log, ring signatures / stealth pseudonyms, TPM2 / Nitro attestation.

It explicitly is **not** a human IdP and explicitly does **not** do application-layer authorization or prompt-injection defense.

## 3. Technical findings by severity

### CRITICAL

**C-1 — TPM2 "hardware attestation" trust binding is broken.** `verify_tpm2_quote` walks the AIK cert chain to a vendor root, but verifies the quote signature with a **separate, client-supplied** pubkey (`ctx.trusted_pubkey_b64u`, set at registration from `tpm2_attestation_pubkey_b64u`). The two checks are unrelated; the verifying key is never extracted from the validated cert's SPKI. An attacker presents any genuine vendor-rooted cert + a quote signed by their own key and passes both checks. `core/src/attestation/tpm2.rs:621-628`, `core/src/agent.rs:636-646`. This is the *only* defense against the host-compromise attack the threat-model admits it can't otherwise stop — and it doesn't work.

**C-2 — Dashboard has no authentication; tenant is self-service.** No login, no session, no auth middleware anywhere. Reaching port 3000 = full admin control of the core (list/revoke agents, upload/delete policies, read all users/clients, trigger anchors, export audit, drive the live LLM agent). The `sauron_tenant_id` cookie is written client-side to any string and forwarded unvalidated as `x-sauron-tenant-id`. `dashboard/middleware.ts`, `dashboard/lib/tenant.ts:52`, `dashboard/app/api/_proxy.ts:27-39`. Acceptable only if 3000 is gated by an external network layer (verify the deploy Caddyfile/SSH tunnel); Critical if internet-reachable.

### HIGH

**H-1 — Multi-tenancy is honor-system, not enforced.** Tenant id comes from the unauthenticated `x-sauron-tenant-id` header; admin static keys are global (tenant-blind); there is no DB-level RLS/role defense-in-depth. The admin plane forgets the `tenant_id` filter on `get_agents`, `get_users` (returns names + nationality + email), `revoke_agent_admin`, per-agent metrics, egress. A single admin key + any tenant header reads/writes any tenant. `core/src/tenancy/mod.rs:160-197`, `core/src/admin.rs:792,808,854,1057,1101,1170,1242`, `core/src/routes.rs:275-279`.

**H-2 — "Tamper-evident security audit log" has no integrity.** `security_audit_log` rows are bare INSERTs with no `prev_hash`, no HMAC, no sequence numbers. Any DB writer silently edits/deletes. The one "audit report" HMAC is keyed on the shared `token_secret` (held by the operator) and signs un-integrity-checked source rows. `core/src/middleware/audit_log.rs:264-275`, `core/src/db.rs:614-620`, migration `0007`.

**H-3 — A-JWT is symmetric / server-forgeable despite EdDSA framing.** Agent signing seed = `SHA-256(jwt_secret ‖ agent_id ‖ human_key_image ‖ agent_checksum)`. Whoever holds `jwt_secret` mints a valid token for any agent. The real agent-held proofs are the PoP and ring keys, not the A-JWT. `core/src/agent.rs:81-97,156,183`.

**H-4 — ZK verifier proves a weaker statement than claimed + forgeable dev keys.** The verifier binds `public_inputs[1]` to the Merkle root but never asserts `public_inputs[0]` (the circuit's `valid` output) `== 1`. A sound proof of a *failed* predicate is accepted. Shipped vkeys are self-labeled "DEV ONLY - forgeable"; fail-closed only when the runtime resolves to "production" (env-string dependent, defaults to prod when unset). `core/src/zk_verifier.rs:154-243,287-314`, `core/src/aggregation/verify.rs:138-141`.

**H-5 — Nitro attestation fails open by default.** Cert-chain validation runs only if `SAURON_NITRO_ROOT_PEM` is set; otherwise the COSE signature is checked against a self-asserted leaf. A JSON dev-blob with no signature is accepted unless `SAURON_NITRO_REJECT_DEV_MODE=1`. Both guards default off. `core/src/attestation/nitro.rs:120-193`, `core/src/attestation/cbor.rs:1079-1081`.

**H-6 — Differential-privacy accounting is leaky.** Four correlated quartile queries over the same dataset are charged as one ε (`publish.rs:227,265-270`). The lifetime budget is operator-resettable via `rotate_cycle` with no min-cycle guard and no audit event (`dp/ledger.rs:369-411`). The non-ledger `publish_cohort` enforces no inter-publication budget → repeated-publish averaging attack recovers near-raw quartiles. The DP ledger is SQLite-only — on a Postgres backend, ε accounting silently diverges from the data store.

**H-7 — Bound-policy enforcement fails open.** Any error in `enforce_bound_policy_for_action`, or a binding that points at an absent policy, falls through to *allow*. For an enforcement product the core path should fail closed in `enforce` mode. `core/src/main.rs:3578-3584`, `core/src/policy/handlers.rs:737-746`.

### MEDIUM

- **M-1** Agent→policy binding is a plain DB row, not cryptographically bound to the agent identity; its own docstring calls it "advisory" while the enforce path treats it as authoritative. `core/src/policy/binding_handlers.rs`.
- **M-2** `CrossTenantAttempt` audit/tripwire event is constructed only inside a `#[test]` — never emitted in production. `core/src/middleware/audit_log.rs:581`.
- **M-3** Revoked agents are never removed from the in-memory global ring; ring grows unbounded across tenants and revoked pubkeys persist as valid decoys (memory/DoS + privacy-set integrity). `core/src/agent.rs:932`.
- **M-4** SSRF via the agent runner: `/api/agent/run` forwards the raw body to the Python runner whose `web_fetch(url)` does `requests.get` on any URL (no allowlist, no block on `169.254.169.254`/RFC-1918). `scripts/demo/agent_runner.py:136`.
- **M-5** A-JWT `verifyAgentToken` (SDK) doesn't pin `iss` or enforce a max token age by default; `JtiReplayGuard` is in-memory, unbounded, single-process, and opt-in. `sdk/typescript/src/ajwt.ts:391-396,157-172`.
- **M-6** Paillier decryption is not constant-time and there is no range proof on submitted ciphertexts (a client can bias the aggregate with `Enc(huge)`). Documented `NEEDS_CRYPTO_REVIEW`. `core/src/he/paillier.rs:282-296`, `core/src/aggregation/he_aggregator.rs:111-124`.
- **M-7** Mutating admin ops aren't recorded to the security audit log with actor identity; `AdminKeyRotated` is never emitted.

### LOW

- DSL footgun: `Null in (...)` ⇒ Allow, combined with `payment_currency` hardcoded Null, makes every DSL currency-allowlist a dead no-op (net product saved by a separate check). `core/src/policy/expressions/eval.rs:120,201`.
- 154 `.unwrap()` in `main.rs`; a poisoned lock cascades to 500s.
- Partner `private_key_hex` stored plaintext at rest. `core/src/admin.rs:360`.
- Upstream core error bodies (potential stack/SQL traces) passed verbatim to the unauthenticated browser.
- `NEXT_PUBLIC_CORE_URL` inlined into the client bundle (low-risk topology leak, contradicts "browser never sees core URL").
- `integrity-proof.ts` uses `eval("require")`; HE `normalise()` never validates the public key despite its own disclaimer.

### What is genuinely solid (credit where due)

- **Policy DSL evaluator** — closed function whitelist, NaN/Inf and type-confusion fail-closed, full-input parse, thorough unit tests. Production-quality. `core/src/policy/expressions/{parser,eval}.rs`, `compiler.rs`.
- **The per-call leash** — PoP Ed25519 + single-use nonce + constant-time config digest, server-enforced regardless of SDK use; TS/Rust payloads byte-identical. `core/src/agent.rs:1562-1720`, `sdk/typescript/src/call-sig.ts`.
- **SQL fully parameterized** on both rusqlite and sqlx; **TOCTOU/replay** paths serialized (`BEGIN IMMEDIATE` / `SERIALIZABLE` + 40001 retry). No injection found.
- **Solana anchoring** is fully real and externally verifiable.
- **Paillier HE** correct and actually used; **ring sigs + stealth pseudonyms** correct (dormant).
- **`empirical-suite.ts`** (16 real HTTP attacks) is regenerated and CI-gated 16/16 by `release-gate.yml`; **`dp_properties.rs`** is rigorous property testing.
- **Documentation honesty** — explicit "Cannot do" / "claims a seller should NOT make" / pervasive `NEEDS_CRYPTO_REVIEW`. Rare and creditable.

## 4. Where the "proof" is theater

- The marketed "~55 red-team scenarios": the ~46-file Sprint-12/Sprint-3 battery is invoked by **zero CI workflows**, `skipped()` returns `pass:true` (green against no server), proof-forgery tests submit `{}` and accept *any* rejection (can't prove the verifier discriminates), and `dp-cohort-deanonymize` is a tautology (`variance>0 || allIdentical`). `redteam/src/scenarios/_s12_lib.ts:94-102`, `proof-tampered-root.ts:34-54`, `dp-cohort-deanonymize.ts:98`.
- Competitive benchmark: real distributed `sauron-core` (DB + nonce + verify) vs **in-memory localhost echo servers** for DPoP/http-sig — not a head-to-head; `integration_loc` is hand-typed with Sauron uniquely credited `server:0` (the headline metric, biased in its favor); 3/5 competitors are vapor (`aws-sts` throws, `auth0` needs live creds); all result JSONs are stale committed fixtures. `redteam/src/benchmarks/competitive.ts:85,389,883`.
- `tavily-redteam-results.json` was produced with `tavily_search_enabled:false` — static payloads, not an "autonomous threat-intel agent."
- Cross-tenant Rust test asserts a `WHERE tenant_id=?` clause the live handler does **not** run — it tests SQLite, green-lighting an admitted open gap. `core/tests/multi_tenancy.rs:462-515`.

## 5. Business audit

**Product (plain terms):** a cryptographic leash for AI agents — stops a hijacked agent from replaying tokens, tampering with requests, drifting its config, escalating delegated scope, or acting after revocation, with on-chain tamper-evident audit. Sits next to your existing auth; governs only the agent layer.

**Problem & ICP.** The problem ("who stops a hijacked agent that spends money / touches systems?") is real and 2026-timely. But the clean-fit ICP is narrow and the docs admit it: a greenfield agent-SaaS startup with no existing IdP, security-mature enough to want fail-closed per-call signing, and willing to self-host a one-author Rust binary. The acute-pain buyer (regulated enterprise) is explicitly told *not* to use it for the regulated path. Those constraints rarely co-occur.

**Market & TAM.** Real, hot, but crowded and consolidating. The specific slice SauronID owns — cryptographic per-call binding with on-chain audit, self-hosted — is a thin sliver. On-chain anchoring narrows it further: most enterprises view "our audit log is on a public blockchain" as risk, not feature (and it smells of the Solana-hackathon provenance).

**Competition / moat.** Thin. Every primitive is off-the-shelf and the team itself says "the win is the combination, not any single feature":

| Competitor | Overlap | Edge / lack |
|---|---|---|
| OAuth 2.0 DPoP (RFC 9449) | Key-bound tokens, replay | DPoP is standardized + vetted libs; team concedes it blocks ~10/16 and is "closest" |
| HTTP Message Signatures (RFC 9421) | Body integrity, per-call signing | SauronID's core mechanism is a custom re-spin of this; http-sig benches *faster* |
| Cedar / OPA / OpenFGA | Policy engine | SauronID's policy layer is a shallow subset; no edge — and it admits no app-layer authz |
| Okta/Auth0 "Auth for GenAI", MS Entra Agent ID, AWS | Agent identity, delegation, revocation | Incumbents win on certs, ecosystem, managed multi-region, procurement |
| Lakera / Protect AI / Guardrails / NeMo | "AI agent security" budget | Own the budget + the attack buyers fear (injection) — which SauronID does NOT defend |
| LiteLLM / Portkey / Cloudflare AI Gateway | Egress/budget/audit | Gateways own the in-path position; SauronID's own idea doc concludes "front LiteLLM" |
| AWS Nitro / SGX / Azure CVM | Hardware attestation | The one true defense against host compromise — and SauronID's is broken/stubbed |

**Moat verdict:** weak — an integration, not an invention. Genuinely sharp bits: fail-closed per-call binding as a single self-hostable binary (nice DX, ~25 LoC client integration), and the documentation honesty. Over-engineered for any customer that exists today: dual-chain anchoring, custom DP/HE, 7-platform attestation enum (6 stubbed), custom ZK on dev keys.

**Maturity-to-revenue.** Demo/staging-grade by the docs' own admission. Blockers: no SOC2/ISO, single-node SQLite default (partial Postgres, internal doc inconsistency on how many modules ported), ZK on forgeable dev keys, unaudited DP/HE, every hardware-attestation verifier except `ed25519_self` is `NotImplemented`, multi-tenancy partial. Realistically 6–12+ months of hardening before clearing even an SMB security review. The compliance docs (subpoena-response, privacy-model) are well-written but position ahead of substance ("trust the operator" + unaudited crypto won't satisfy a compliance officer).

**Business model / GTM — the biggest gap.** There is **no pricing, no monetization, no GTM, no managed-offering plan anywhere in the repo**. The README-referenced pitch deck isn't on disk. Effort went into a branded demo (runbook, read-aloud script, brand book), not a commercial model. A self-hosted Rust binary monetizes poorly without the managed control plane the incumbents already sell — which SauronID explicitly hasn't built.

**Top business risks:** (1) no business model; (2) thin/cloneable moat; (3) solves a second-order problem, not the one buyers fear; (4) differentiators are dev-key/unaudited/stubbed; (5) on-chain anchoring is a procurement liability; (6) single-author, bus-factor-1, no third-party audit.

## 6. Prioritized remediation (if continuing)

**Make claims true or drop them:**
1. Bind the TPM2 verifying key to the validated cert SPKI; ignore client-supplied pubkey (C-1).
2. Assert ZK `public_inputs[0]==1`; run a real trusted-setup ceremony before any "ZK proven" claim (H-4).
3. Add real audit-log hash chaining + sequence numbers, or stop calling it tamper-evident (H-2).
4. Either make the A-JWT agent-held asymmetric, or stop marketing it as verifiable identity (H-3).

**Close the isolation/auth holes:**
5. Bind tenant to the credential (per-tenant keys/JWT), add `tenant_id` to every admin query, add Postgres RLS as defense-in-depth (C-2/H-1).
6. Add real auth to the dashboard; server-side tenant authz; validate the tenant cookie (C-2).
7. Make bound-policy enforcement fail **closed** in `enforce` mode; default Nitro chain validation on (H-5/H-7).

**Privacy correctness:**
8. Fix DP composition accounting for correlated quartiles; guard `rotate_cycle`; port the ledger to Postgres; add range proofs + constant-time HE (H-6/M-6).

**Stop the theater:**
9. Make red-team scenarios fail closed when the server is down; assert positive cases (valid proof accepted); wire the battery into CI or delete it.
10. Either rebuild the competitive benchmark as a true head-to-head or remove the LoC/latency claims.

**Then** decide the business question: narrow hard to the one greenfield ICP and build a managed plane + SOC2, or treat this as an acqui-hire/portfolio engineering showcase.

---

## 7. Bottom line

- The **core leash is real, server-enforced, and well-built** — and the policy DSL and per-call signing are production-quality.
- The **headline differentiators are not production-safe**: TPM2 attestation is broken, ZK is unsound + dev-key, Nitro fails open, the "tamper-evident audit log" has no integrity, and multi-tenant isolation is an unauthenticated header on a god-mode admin key.
- The **"proof" layer is partly theater**: one real CI-gated 16-attack suite, surrounded by ~46 CI-dead self-confirming scenarios and a non-defensible benchmark.
- The project is **unusually honest in its docs** about most of these gaps — which both raises trust and confirms how far from done it is.
- **There is no business** — strong engineering and intellectual honesty, but pre-product and pre-revenue, a thin moat over off-the-shelf primitives, and no pricing/GTM/monetization in the repo.

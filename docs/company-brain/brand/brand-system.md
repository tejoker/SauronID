# SauronID Brand System v2.0

**Master line:** Build agents you can actually let act.  
**Descriptor:** The agent platform with boundaries built in.  
**Version:** 2.0 - August 2026

> This version reflects the shift from a security-first infrastructure product to an accessible agent creation and execution platform whose control system is native to every agent. Product claims must remain aligned with `SauronID_Product_Truth_v2.md`.

## 1. Brand core

### Purpose

Make useful AI agents accessible without asking people to surrender control.

### Brand promise

Every SauronID agent starts with a clear job, receives only the capabilities it needs, and stays inside boundaries the agent cannot rewrite.

### Vision

People should be able to delegate real work to AI with the same clarity they expect when delegating to a trusted colleague: a defined objective, explicit authority, visible limits, and accountable results.

### Category

**Internal category:** intent-governed agent platform.  
**Market-facing descriptor:** agent platform with boundaries built in.

### Positioning statement

For business operators and teams that want AI agents to do real work, SauronID is a platform for building and running agents with explicit intent, capabilities, and enforceable boundaries. Unlike a generic agent builder or a security layer added after deployment, SauronID makes the boundary part of the agent from the moment it is created.

### Strategic shift

| Old center of gravity | New center of gravity |
|---|---|
| Sell security for agents | Enable people to build useful agents safely |
| Technical/security buyer first | Operator/builder first, technical validator second |
| Integrate a protection layer | Create the agent inside a controlled environment |
| Fear and risk reduction | Capability, adoption, and confidence |
| Repository and infrastructure | Guided launcher now, managed cloud later |
| Inspect architecture | Build the first agent |

### Brand principles

1. **Capability before fear.** Show what the agent can accomplish before explaining the risk model.
2. **Boundaries made visible.** Limits must be understandable, testable, and explainable.
3. **Progressive power.** A first-time builder can start simply; experts can inspect and configure deeply.
4. **Local freedom, shared control.** The execution mode may change; the agent's contract should not.
5. **Proof without theater.** Use technical evidence where it earns trust, not as decoration.

## 2. Audience

### Primary user

An AI-forward business operator or domain expert who:

- already uses ChatGPT, Claude, or simple automation tools;
- wants to automate a recurring workflow;
- understands the job better than the underlying AI stack;
- is not necessarily a developer;
- needs the agent to touch real tools or data;
- is uncomfortable giving it unrestricted authority.

Representative roles:

- Operations and Product Operations
- Revenue Operations and Growth Operations
- Finance Operations
- Customer Support Operations
- Research and Analyst roles
- Founders and small-team leaders

### Champion

The person who builds the first useful agent and proves the workflow to colleagues.

### Technical validator

IT, platform, security, or engineering validates the runtime, secrets, policies, network boundary, and audit behavior.

### Economic buyer

A functional leader who pays for hosted execution, collaboration, shared controls, and reliability after individual value is proven.

### Not the first target

- organizations that are not willing to try AI agents at all;
- hobbyists seeking unrestricted autonomous systems;
- enterprise security teams evaluating only an infrastructure gateway;
- mission-critical autonomous decisions that cannot begin with human approval or reversible actions.

## 3. Customer problem

The customer does not wake up asking for cryptographic authorization for agents.

They ask:

- How do I make an agent do this job?
- Which model should I use?
- How do I connect it to my tools?
- What happens if it does the wrong thing?
- Can I control spending, data access, or irreversible actions?
- Can I understand why it was stopped?
- Can I start without an engineer or a procurement project?

SauronID should answer those questions in that order.

## 4. Product model

### Now - SauronID Launcher

A downloadable, guided local application for early access.

The intended promise:

- build an agent without GitHub, Docker, or a terminal;
- connect a supported local model or a personal API key;
- configure the job, tools, data, limits, and approvals;
- run locally for free;
- inspect allowed and stopped actions.

Local availability is subject to supported operating systems, hardware, model compatibility, and connector coverage.

### Next - SauronID Cloud

A managed execution mode for users who want broader model access, no local compute dependency, background runs, collaboration, and centralized controls.

Potential commercial models:

- subscription;
- metered model/runtime usage;
- hybrid subscription plus usage;
- customer-provided model keys with platform fees.

Do not finalize pricing language before usage, cost, and willingness-to-pay are measured.

### Product continuity

> **One agent definition. One boundary model. Multiple ways to run.**

## 5. Product grammar

### 1. Intent

The job the agent is expected to accomplish.

Good intent is:

- outcome-oriented;
- specific enough to evaluate;
- separate from the permissions used to accomplish it.

### 2. Capabilities

The models, tools, data, services, and actions available to the agent.

The interface should help the user understand the consequence of each capability before granting it.

### 3. Boundaries

Rules the agent cannot change itself:

- allowed and forbidden actions;
- data scope;
- destinations;
- budgets;
- rates;
- schedules;
- approval thresholds;
- stop conditions;
- time-to-live.

### 4. Run

The execution context:

- local launcher;
- personal model/API key;
- future SauronID Cloud;
- future team or private runtime.

### 5. Proof

A clear answer to:

- what did the agent do?
- what was stopped?
- which boundary caused the decision?
- who approved the agent and action?
- what evidence remains?

## 8. Voice and tone

### Personality

- **Empowering:** assumes the customer can build useful things.
- **Clear:** replaces infrastructure vocabulary with visible consequences.
- **Composed:** does not use fear to manufacture urgency.
- **Precise:** separates what is available, planned, and hypothetical.
- **Responsible:** never confuses control with zero risk.

### Sound like

- a capable product guide;
- a thoughtful operator;
- a calm technical expert when detail is required;
- a platform that wants the user to succeed, not feel intimidated.

### Never sound like

- a hacker-film trailer;
- a fear-based security vendor;
- an AI workforce fantasy;
- a generic no-code automation platform;
- an academic cryptography paper on the homepage;
- a product that guarantees perfect autonomy.

### Preferred vocabulary

build, agent, job, intent, capabilities, tools, boundaries, limits, approval, run, local, model, activity, stopped, explain, control, team.

### Technical vocabulary - use progressively

mandate, policy, signature, one-use capability, receipt, revocation, audit, proof, egress, configuration digest.

### Avoid unless literally true

secure by default, safe, autonomous, trustless, unhackable, zero risk, every model, any computer, fully private, enterprise-ready, audited, compliant, production-grade cloud.

### Copy examples

**Use:** "Choose the tools this agent can use."

**Avoid:** "Provision a least-privilege capability envelope."

**Use:** "Require approval before a payment exceeds EUR500."

**Avoid:** "Military-grade financial agent security."

**Use:** "This action was stopped because the destination was outside the approved list."

**Avoid:** "Threat neutralized."

**Use:** "The launcher uses your model or API key. Model availability depends on your provider and hardware."

**Avoid:** "Run any model, anywhere, for free."

## 13. Visual grammar

### Canvas

Generous light space communicates accessibility and creation. Dark surfaces are reserved for high-focus moments.

### Boundary

A visible frame, rail, range, or checkpoint represents the rules around an agent. Boundaries should look enabling, not imprisoning.

### Path

Show the route from intent to action. Paths may pass through tools, approvals, and outcomes.

### Checkpoint

Use a clear pause or decision node for human approval, risk review, or a stopped action.

### Orbit

Curves from the logo may connect models, tools, and data to the central agent. Use one dominant arc, not decorative fields of rings.

### Aperture

Elliptical framing can focus attention on an outcome or decision. The eye is a compositional principle, not a repeated icon.

### Visual rule

If an element makes SauronID look more "cyber" but does not make the product easier to understand, remove it.

## 15. Motion

### Principle

Motion should help the user understand setup, execution, approval, or interruption.

### Timing

- Micro feedback: 120-180 ms.
- Component transition: 220-320 ms.
- Step transition: 350-500 ms.
- Narrative transition: 500-700 ms.
- Default easing: `cubic-bezier(.22, 1, .36, 1)`.

### Useful motion

- capability connecting to an agent;
- a boundary preview updating;
- a run moving through steps;
- an approval checkpoint pausing the path;
- a stopped action returning to the rule that caused it.

### Avoid

- fade-in-everything on scroll;
- perpetual eye movement;
- ambient scan lines;
- blinking terminal cursors as decoration;
- motion that suggests surveillance;
- confetti for sensitive actions.

Always respect `prefers-reduced-motion`.

## 16. Launcher experience principles

### 1. Outcome before configuration

Ask what the user wants the agent to accomplish before asking about models, keys, or policy.

### 2. Template before blank canvas

Start with a small set of excellent, bounded use cases. Each template should explain its job, tools, limits, and expected result.

### 3. Progressive disclosure

The first run should not expose every policy primitive. Provide a simple setup with optional advanced controls.

### 4. Key setup without anxiety

- explain why the key is needed;
- link directly to the provider's creation flow;
- validate it immediately;
- mask it after entry;
- state where it is stored;
- never expose it in logs;
- support deletion and rotation.

### 5. Preview the boundary

Before the first run, show two examples:

- "This agent can update these CRM fields."
- "This agent cannot delete a contact or send a message without approval."

### 6. Teach through contrast

The first-run demo should include one allowed action and one deliberately stopped action.

### 7. Explain, do not merely deny

A stopped action should display:

- what the agent attempted;
- which boundary applied;
- what the user can change;
- whether approval is possible.

### 8. Keep technical depth available

Experts should be able to inspect:

- the mandate;
- policy representation;
- signatures;
- receipts;
- provider and runtime details;
- logs and export.

## 20. Claims governance

### Claim pattern

`Outcome -> mechanism -> evidence -> limitation`

Example:

- **Outcome:** The agent cannot send to an unapproved destination through the protected path.
- **Mechanism:** The gateway checks the destination against the server-side boundary and consumes a one-use capability.
- **Evidence:** The stopped action and rule appear in Activity.
- **Limitation:** Production deployment must prevent direct egress around the gateway.

### Required labels

- **Available now** - verified in the released product.
- **Early access** - packaged product being tested with a defined cohort.
- **Coming later** - planned, no availability promise.
- **Exploring** - commercial or product hypothesis.

### Final test

If a customer could reasonably interpret the statement as a promise about availability, model support, security, privacy, compliance, or autonomy, verify it against the product truth file before publishing.

## 21. Brand governance

Before publishing:

- verify product claims against the current repository and release;
- confirm launcher and cloud availability labels;
- confirm model/provider and operating-system support;
- test WCAG contrast, keyboard focus, and reduced motion;
- keep one canonical logo and token source;
- avoid hard-coded security statistics without reproducible evidence;
- keep the technical architecture accessible but secondary;
- run real onboarding sessions with non-technical users;
- update this system when the launcher, cloud, or pricing becomes real.

### Final brand rule

> **SauronID should make agency feel possible and boundaries feel natural.**
